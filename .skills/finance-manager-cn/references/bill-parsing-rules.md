# 账单文件解析规范（格式无关）

本文件是**硬性要求**。核心原则：**不得针对任何单一支付平台或银行硬编码格式**。必须实现一套通用的"表头发现 + 列语义映射 + 兜底交互"流水线，使支付宝、微信、云闪付、京东支付、各家银行借记/信用卡、PayPal、Stripe、以及未知来源的导出文件都能解析。

下文出现的具体列名（如 `金额（元）`、`收/支`）**仅作示例**，不得作为匹配依据写死。

---

## 一、核心原则

1. **不硬编码厂商**：不写 `if (isAlipay)` 这类分支来决定列位置。所有来源走同一条通用流水线。
2. **按语义识别，不按位置识别**：列的含义由列名语义推断，不依赖列序号或固定行号。
3. **无法自动识别时降级到用户交互**，而不是直接报"文件格式不正确"。
4. **能解析多少就先解析多少**：部分字段缺失应允许用户补充映射，而非整单失败。

---

## 二、标准解析流水线（六步，顺序不可颠倒）

```
1. 编码检测/解码  →  2. 表头行定位  →  3. 列语义映射
                                            ↓
6. 结果校验  ←  5. 值清洗与归一  ←  4. 收支方向判定
```

### 步骤 1：编码检测与解码

- 支持 UTF-8（含 BOM）、GBK / GB18030、UTF-16LE/BE、Big5。
- 国内账单 CSV 常为 **GBK/GB18030**；海外多为 UTF-8。
- **必须先正确解码再做后续任何匹配**，否则列名全是乱码，映射必然失败。
- 解码失败时报明确错误（"编码识别失败，请另存为 UTF-8 CSV"）。

### 步骤 2：表头行定位（不得依赖固定行号）

导出文件常在数据前带若干行说明（账号、统计区间、免责声明等），行数各家不同（0 到 20+ 行）。

算法要求：
- 扫描**前 30 行**（Excel 则对每个工作表扫描）。
- 对每一行计算"**表头得分**"：该行有多少个单元格能命中下文字段概念别名词典。
- 取得分最高且**至少命中"日期概念"与"金额概念"各一个**的行作为表头行。
- **禁止**硬编码行号；**禁止**用"跳过以 # 或空格开头的注释行"这类粗暴规则（会把真表头一起跳掉）。
- 若无任何行达标 → 进入第七节的兜底策略。

### 步骤 3：列语义映射（标准化 + 别名 + 模糊匹配）

标准化函数（中英文列名统一走这一个函数，Excel 与 CSV 路径**必须共用**）：

1. 去掉括号及括号内内容（全角 `（）` 与半角 `()` 都要处理）。
2. 去掉空格、制表符、不可见字符。
3. 全角转半角。
4. 转小写。
5. **保留 `/` 与 `-`**（`收/支`、`借/贷`、`Dr/Cr` 依赖它们）。

匹配顺序：精确命中别名 → 别名包含关系 → 编辑距离模糊匹配。

> 反例：直接用完整字符串精确匹配 `金额`，遇到 `金额（元）` / `金额(元)` / `交易金额` 全部落空，导致金额列索引为 -1、所有行金额为 0 被跳过，表面现象就是"提取不到交易记录"。

### 步骤 4：收支方向判定

见第四节，必须支持四种模式，不能只实现一种。

### 步骤 5：值清洗与归一

见第五节。

### 步骤 6：结果校验

- 有效行数为 0 → 报错并说明是"表头未识别"还是"金额全为空"。
- 抽样校验：日期能解析、金额为有效数值、方向已判定。
- 统计并回报：识别行数 / 跳过行数 / 跳过原因分布。

## 四、收支方向的四种模式（必须全部支持）

| 模式 | 特征 | 处理方式 |
| --- | --- | --- |
| A. 方向列 + 单金额列 | 有独立方向列（如 `收/支`、`借/贷`、`Type`） | 按方向列取值判定；金额取绝对值 |
| B. 收入 / 支出双列 | 两个金额列，各行只有一列有值 | 哪列有值即为该方向；常见于银行流水（借方/贷方发生额） |
| C. 金额正负号 | 单金额列，支出为负、收入为正 | 按符号判定；注意括号负数写法 `(123.45)` 也表示负 |
| D. 无方向信息 | 只有金额且全为正 | **不得擅自假设方向**；提示用户选择默认方向或做列映射 |

方向值判定红线：

- 方向列取值需**精确匹配**归一化后的值，并维护一份"中性/非收支"值集合，例如：`不计收支`、`不计收支`类中性项、`转账`、`内部转账`、`Transfer`、`Neutral`。
- **禁止**用 `includes('收')` 这类子串判断——`不计收支` 含"收"字会被误判为收入。同理 `Debit`/`Credit` 不能用首字母判断。
- 中性项应**排除或单独标记**，不计入收入或支出（常见于退款、内部转账、理财赎回、还款）。
- 借贷方向的语义在不同机构可能相反（站在账户视角 vs 站在银行视角），**必须依据余额变化或双列位置校验**，不得直接假设"借=支出"。

## 五、值清洗与归一规则

### 金额

- 去除千分位分隔符、货币符号（`¥ ￥ $ € £ HK$` 等）、空格、全角字符。
- 支持括号表示负数：`(123.45)` → `-123.45`。
- 支持中文单位残留（如尾部 `元`）。
- 解析失败的行**跳过并计数**，不要静默丢弃。

### 日期

- 支持多种格式：`YYYY-MM-DD`、`YYYY/M/D`、`YYYY.MM.DD`、`YYYYMMDD`、`DD/MM/YYYY`、`MM/DD/YYYY`、带时间的 `YYYY-MM-DD HH:mm:ss`、中文 `2026年7月1日`。
- **`DD/MM` 与 `MM/DD` 有歧义**：应基于整列样本推断（若某位置出现 >12 的值即可定序），无法推断时询问用户，不得默认。
- Excel 单元格中的日期常为**序列号**（1900 起算），必须转换。

### 文本

- 去首尾空白与不可见字符。
- 账号/卡号类字段**必须脱敏**，仅保留后四位入库与展示。

## 六、按文件类型选择解析方式（禁止混用）

| 文件类型 | 必须这样做 | 严禁这样做 |
| --- | --- | --- |
| `.xlsx` / `.xls` | Edge Function 内用 **SheetJS**（`npm:xlsx`）解析二进制，遍历**所有工作表** | 用 `TextDecoder` 把二进制当文本读（必然乱码） |
| `.csv` / `.txt` | **状态机**逐字符解析，跟踪引号开合 | `split(',')`（末尾列被截断、含逗号字段错位） |
| 分隔符变体 | 自动探测分隔符：`,` `;` `\t` `|` | 假定一定是逗号 |
| `.pdf` | 前端 **`pdfjs-dist`** 逐页提取文本，再交给 `@文本生成大模型` 结构化 | 传空字符串占位 |
| 扫描版 PDF / 图片 | 走 `@文档格式转换`（PDF/图片 → Excel），或提示用户导出 CSV | 直接把图片字节喂给模型 |

`.xlsx` 底层红线（若不得已需底层处理）：单元格文本多在 `xl/sharedStrings.xml`，`<c t="s"><v>5</v></c>` 中的 `5` 是**索引而非数值**，必须解引用；用 SheetJS 可自动规避。

## 七、三级兜底策略（关键：解决"任意来源"）

**Level 1 — 自动映射成功**：表头与必需字段全部命中 → 直接导入，并向用户展示识别结果摘要（识别到的列 → 概念）供快速确认。

**Level 2 — 部分识别，进入交互式列映射**（必须实现）：
- 展示解析出的前若干行预览表格。
- 为每一列提供下拉框，让用户手动指定其语义（日期 / 金额 / 方向 / 商户 / 忽略…）。
- 记住该来源的映射方案，下次同类文件自动复用。
- 这是支持**任意支付平台与银行**的根本手段，不能省略。

**Level 3 — 完全无法识别**：
- 可调用 `@文本生成大模型`，把**表头行与前几行样本**（脱敏后）交给它做语义映射猜测，再让用户确认。
- 同时提供一份**通用模板 CSV**（日期、金额、方向、对方、摘要、分类）供用户整理后上传。
- 报错必须说明卡在哪一步。

## 八、Edge Function 编辑红线

重写 Edge Function 时容易残留旧代码，导致部署即崩：

```
InvalidWorkerCreation: worker boot error: Uncaught SyntaxError:
Identifier 'corsHeaders' has already been declared
```

- **必须整文件覆盖**重写，不得在原文件后追加新实现。
- 改完**必须检查文件末尾无旧代码残留**（顶层常量、`import` 出现两份即报上述错误）。
- 部署前自查：全文搜索 `corsHeaders` 及各 `import`，每项应**只出现一次**。

## 九、失败必须给出可操作的报错

- **禁止**返回乱码或空结果后继续走后续流程。
- 报错必须指出**具体卡点**与**下一步动作**，例如：
  - "未识别到金额列（已尝试匹配：金额 / 金额（元）/ 交易金额 / amount / debit / credit），请手动指定列。"
  - "已定位表头但 128 行中 0 行金额可解析，疑似金额列含非数值内容。"
  - "未能从 PDF 中提取文本，该文件可能是扫描件，请改用图片转 Excel 或导出 CSV。"
  - "文件编码疑似 GBK，解码失败，请另存为 UTF-8 CSV。"
- **禁止**只抛"请检查文件格式是否正确"——这句对用户无任何指导价值，且会掩盖真实根因。

## 十、数据完整性与安全红线（导入之后同样适用）

以下每条都是通用正确的财务处理要求，与来源无关。

### 1. 金额禁止用浮点数运算

- **必须**以**整数「分」**（或 decimal 类型）存储与累加，仅在展示层格式化为元。
- 禁止用 JS `number` 直接累加金额：`0.1 + 0.2 !== 0.3`，数千行累加会产生分位误差，导致对不上账。

### 2. 存储与下载必须私有

- 账单文件属高敏数据，**所有存储桶必须私有**。
- 导出文件通过**签名 URL（短过期）**下载，**严禁放公开桶**——公开桶意味着任何拿到 URL 的人都能下载他人流水。

### 3. 多用户必须做数据隔离

- 若应用有登录 / 多用户，交易表、导入批次表**必须启用 RLS 并按 `user_id` 隔离**。
- 所有查询走当前登录用户身份，禁止在客户端传 `user_id` 作为过滤条件。

### 4. 重复导入必须幂等去重

- 同一份账单被导入两次，或两次导入的时间区间重叠，都很常见。
- 去重键优先取**交易单号 / 流水号**；无单号时用 `日期 + 金额 + 方向 + 对方 + 摘要` 生成稳定 hash。
- 在数据库层加**唯一约束**，重复行跳过并计数回报，而不是静默插入。

### 5. 内部转账与退款必须识别（标记，不静默删除）

- **内部转账**：同一用户从 A 账户转到 B 账户，两个账户都导入后会产生"一笔支出 + 一笔收入"，导致**收入与支出双双虚高**。需按"金额相同、方向相反、时间接近、跨账户"配对识别。
- **退款**：应与原支出配对抵消，否则支出虚高。
- **红线**：配对属于启发式判断，**必须标记为疑似内部转账/退款并由用户确认**，不得静默删除或直接改写数据。

### 6. 信用卡账单与银行流水语义不同

- **信用卡还款是转账，不是支出**。若同时导入了信用卡消费明细，把还款计为支出会造成同一笔消费被计两次。
- **账单周期**（账单日 / 还款日）与自然月不一致。做月度报告时必须说明统计口径是自然月还是账单周期。
- 分期付款需明确口径：按期确认，还是在消费当期一次性计入。二者不可混用。

### 7. 多币种不得直接相加

- 不同币种的金额**禁止直接求和**。
- 必须按币种分组统计；若需折算，必须标注**汇率来源与汇率时点**。

### 8. 发给大模型前必须脱敏

- 账单文本在交给 `@文本生成大模型` 之前，**必须脱敏**：账号 / 卡号仅保留后四位，去除姓名、身份证号、手机号等可识别信息。
- 只传分析所必需的字段，不整份原文照发（最小必要）。

### 9. 大模型结构化输出必须校验

- **禁止**用正则抠出 JSON 后直接 `JSON.parse` 就当结果使用。
- 必须做 **schema 校验**（字段存在性与类型），校验失败则重试或明确降级报错。
- 模型返回的数值必须再次做数值合法性校验，不可直接入库。

### 10. 原始文件留存策略必须明确

- 解析完成后，需有明确的原始文件留存策略（保留多久、何时清理、用户能否主动删除），并在产品中告知用户。
- 不得无期限地留存用户的原始账单文件。
