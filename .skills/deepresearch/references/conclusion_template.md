# 结论与反思模板

任务结论保存本任务中可核验、可复用的研究判断；反思结论只记录对已有结论的检查、修正和补充。

**保存要求**：任务结论和反思结论必须通过 `<SKILL_ROOT>/scripts/save_conclusion.py` 保存，不得直接创建或编辑目标文件。任务结论使用 `--type task --task-id N`，反思结论使用 `--type reflection --round N`。

---

## 一、任务结论

**保存路径**：`<PROJECT_ROOT>/outputs/conclusions/task_N.md`

````markdown
### 任务 N：任务标题

**对应研究问题或主题**

- 本任务实际回答的问题或覆盖的主题

**结论摘要**

用 1—3 句话直接回答本任务，不描述搜索过程。

**关键结论**

1. **核心结论或比较结果**：写出本任务的一条重要结论。

   如果取得同指标、同单位、同时间范围、同统计口径下至少 3 个对象或时间点的数据，可以在这里用紧凑表格集中保留：

   | 对象或时间点 | 核心指标 | 数值 | 单位 | 同比或变化 | 排名或份额 |
   |---|---|---:|---|---:|---:|
   | 对象 A | 指标名称 | 数值 | 单位 | 数值 | 数值 |
   | 对象 B | 指标名称 | 数值 | 单位 | 数值 | 数值 |
   | 对象 C | 指标名称 | 数值 | 单位 | 数值 | 数值 |
   | 合计或其他 | 指标名称 | 数值 | 单位 | — | 数值 |

   - 重要事实、数据或案例：保留直接支撑该结论、且后续报告可能使用的信息；没有则省略。
   - 依据：[来源标题](https://具体URL)
   - 依据（计算）：说明合计、占比、增速或“其他”的计算方法；没有则省略。
   - 口径或限制：说明时间、地区、对象、单位、版本、样本或统计口径；没有则省略。

2. **其他关键结论**：写出另一条能够直接回答本任务的结论。

   - 重要事实、数据或案例：保留直接支撑该结论、且后续报告可能使用的信息；没有则省略。
   - 依据：[来源标题](https://具体URL)
   - 口径或限制：没有则省略。

3. 根据本任务实际内容继续编号，不限定关键结论数量。

如多条关键结论能够共同形成一个新的整体判断，可以在最后增加一条“综合判断”；没有新的判断时不必添加。

**信息缺口与写作提醒**

- 尚未取得可靠信息的内容。
- 哪些结论需要使用限定表述。
- 若课题需要横向比较、排名或趋势但本任务尚未取得合格可比数据组，明确写"尚未取得可用于横向比较的同口径定量数据"。
- 没有明显缺口时，写"未发现影响结论使用的重大信息缺口"。
````

允许使用以下依据形式：

```markdown
- 依据：[网页来源标题](https://具体URL)
- 依据（文件）：本地原始文件路径
- 依据（计算）：输入数据、计算方法或结果文件
- 依据（综合判断）：说明根据哪些已有事实以及什么标准得出
```

要求：

- 每条关键结论只表达一个中心判断。
- 每条关键结论紧跟自己的依据。
- 结论中的日期、数字、排名和版本必须与依据一致。
- 摘要与关键结论之间不得存在数量、分类或时间矛盾。
- 网页依据必须提供来源名称和具体URL。
- search和fetch返回的信息都可以使用，但结论不能超出实际获得的信息。
- 使用search返回信息时，只采用返回内容明确表达的事实；上下文、版本或统计口径尚未核对时，在"口径或限制"中说明。
- fetch失败只表示当前接口没有取得正文，不表示网页不存在或信息错误。
- 产品发布时间、功能、版本和机构立场优先使用发布方官方材料。
- 学术观点和实验结果优先使用原始论文、数据集或作者项目页。
- 开源项目的功能、版本和许可证优先使用官方仓库及项目文档。
- 市场、人口、财务和统计数据优先使用统计机构、监管机构、财报、行业协会或原始数据集。
- 厂商资料可以证明厂商如何陈述，但不能单独证明其产品"最好""领先"或"SOTA"；独立评价优先使用公开基准或第三方评估。
- 一个直接、适用的来源可以支持简单事实；比较、趋势、共识、排名和综合判断需要多个相互独立的来源。
- 多个转载同一原始消息的页面不算多个独立来源。
- "依据（综合判断）"只用于分类、比较、筛选和归纳，不能代替日期、数字、排名等事实的来源。
- 使用"首个、第一、唯一、普遍、全部、行业标准、完整、登顶、超越、SOTA"等表述时，来源必须直接支持其比较范围；否则改成有限表述。
- 如果取得同指标、同单位、≥3 个对象或时间点的可比数据，把整组数据放进同一条关键结论，并在"口径或限制"里写明共同评估条件（版本 / 提交设置 / 时间范围等）；例如"在同一版本的 HLE 评估中，系统 A、B、C 分数分别为 26.6%、32.9%、46.4%"。
- 零散、不可比的数字仍写在对应结论行里，不合并成表格，也不为了成图强行合并、外推或取平均。
- 不要求每个任务必须包含数字、反例或自定义框架。
- 禁止使用"多篇文章""相关资料""对应文件""任务N相关资料"等无法定位的依据。
- 不展开成完整章节。

## 二、反思结论

**保存路径**：`<PROJECT_ROOT>/outputs/reflection/round_N.md`

````markdown
### 反思第 N 轮

**检查结果**

只列出确实需要处理的问题。每个问题必须指出对应位置：

- task_N / 关键结论 M：具体存在什么问题。

如果没有问题，只写：

- 本轮未发现需要修正或补充的结论。

**修正与补充**

1. 修正项
   - 位置：task_N / 关键结论 M
   - 原表述：从任务结论中复制需要修改的原句
   - 修正为：可以直接替换原句的完整结论
   - 依据：[来源标题](https://具体URL)

2. 补充项
   - 位置：task_N
   - 补充结论：可以直接加入该任务结论的完整表述
   - 依据：[来源标题](https://具体URL)

如果没有修正或补充，只写：

- 本轮未发现需要修正或补充的结论。

**报告写作提醒**

- 只记录会影响多个任务结论使用的共同限制。
- 没有时写"无额外全局提醒"。
````

要求：

- 反思的产物是对已有任务结论的修改记录，不是研究过程总结，也不是报告写作规划。
- "检查结果"只列问题 + 位置，不写"已覆盖 / 完成情况 / 研究过程总结"。
- 每个检查问题必须对应一个"修正项"或"补充项"；只发现问题、不落成修改的写法禁止。
- 修正项必须包含"位置 + 原表述 + 修正为 + 依据"四段；"原表述"从任务结论中复制原句，不概括。
- "修正为"和"补充结论"必须是可以直接替换或加入结论的完整表述，不能只写"处理建议"或"应……"。
- 证据不足时，直接把原结论改成有限表述（例如"现有公开资料不足以确认……"），不得把问题推迟到报告阶段。
- 「修正与补充」不得记录报告章节安排、附录设计、制图/表格计划、写作风格提醒、下一步工作计划，也不得写"在最终报告中……""在附录中……""补充对 X 的描述"等未落到具体结论修改的表述——这些属于阶段 6，不在结论层出现。
- 没有问题时，"检查结果"和"修正与补充"都只写"本轮未发现需要修正或补充的结论"。
- 不强制每轮必须发现问题。
- 多轮反思按顺序读取，后面的修正覆盖前面的表述。
