# 决策委员会（国内秒哒版）

针对没有明显赢家的模糊决策，组织架构师、怀疑者、实干者和批评者四种视角。价值不在一致同意，而在选择前让分歧、假设和风险清晰可见。

## 前置条件

- 纯文本静态模板无法实现原Skill的“独立意见”核心，因此生成秒哒应用时必须真实组合 `wenxin-text-generation`（展示名：`文本生成大模型`）。
- 普通文本中的 `@名称` 不会绑定能力；生成应用的Query或平台配置必须加载真实Skill标签，生成轨迹应显示依赖。
- 应用运行时对四个角色发起四次相互隔离的模型请求。能并行时并行；不能并行时顺序执行，但后一个角色不得看到前一个角色的答案。
- 只有用户需要登录、跨设备历史、团队共享或决策追踪时才使用Supabase，并按 `user_id` 开启RLS。不要为单次决策引入数据库。

## 使用边界

适用于：

- 多条路径都合理且没有明显赢家；
- 需要显式呈现取舍、反方意见或第二意见；
- 对话锚定可能影响判断；
- 上线/暂停、范围取舍、技术路线或资源配置等Go/No-Go决策。

不适用于：

- 核验答案或代码是否正确；
- 代码、安全审查；
- 拆解明确的实施步骤；
- 系统架构详细设计；
- 直接事实问题；
- 已经明确、只需执行的任务。

遇到不适用请求时直接完成正常分析或执行，不强行召开委员会。

## 四个角色

| 角色 | 关注点 |
|---|---|
| 架构师 | 正确性、可维护性、长期影响与系统完整性 |
| 怀疑者 | 挑战问题框架、拆穿假设、提出最简单可信替代方案 |
| 实干者 | 交付速度、用户影响、资源限制与真实运营 |
| 批评者 | 下行风险、边界情况、失败模式与不可逆成本 |

角色详细提示词见 [角色契约](references/role-contracts.md)。

## 工作流

1. **提炼真实问题**：明确“决定什么、关键约束、成功标准”。信息不足且会改变路线时只补问一个关键问题；否则标注合理假设并继续。
2. **收集最小上下文**：仅保留影响判断的事实、指标、代码片段或限制，不把整段历史对话喂给角色。
3. **先形成架构师初始立场**：在读取其他声音前记录立场、三个最强理由及主要风险，防止综合结论机械跟随多数。
4. **独立运行四个角色**：每个请求只接收规范化问题、最小上下文和自身角色契约；不得接收其他角色输出。每个角色返回立场、三条理由、最大风险和一个容易被忽略的意外点。
5. **偏差防护综合**：逐项比较意见；拒绝某意见时说明原因；外部声音改变结论时明确指出；两名或以上角色反对初始立场时视为真实信号；始终保留最强反对意见。
6. **给出紧凑结论**：先展示四个原始立场，再给出共识、最强分歧、前提检查、推荐方案、触发改道条件和下一步。

默认只运行一轮。用户要求第二轮时，聚焦新问题；仅在必要时提供上一轮结论，并尽量保持怀疑者不受上一轮锚定。

## 应用要求

制作秒哒应用时读取 [国内应用规格](references/miaoda-app-spec.md)。主链路必须为：

`输入决策与约束 → 规范化问题 → 四角色独立分析 → 显示原始意见 → 综合裁决 → 导出/保存`

应用不能只是四段固定提示词或一次模型调用后伪装成四个角色。必须能看到四个独立请求的状态和结果；单个角色失败时只重试该角色，不重复已成功请求。

## 输出格式

按 [裁决模板](references/verdict-template.md) 输出。保持移动端可扫读，不隐藏分歧，不用虚假的票数或置信度制造确定性。事实与假设分开；若输入没有证据，不编造数据。

## 持久化

默认不保存。只有结论真正改变了项目决定且用户要求保存时，才写入应用数据库、项目记录或用户指定位置；保存问题、约束、四个原始意见、最终结论、版本和时间，不写宿主机隐藏路径。
